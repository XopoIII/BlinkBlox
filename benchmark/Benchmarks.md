# Benchmarks

**No tool ran with a limit that refuses traffic.** The bench fires far faster than an honest client,
so every cap is lifted: BlinkBlox's inbound limits (in its definition files), Packet's 8000-byte cap,
QuickNet's rate limit and packet caps, Warp's 8000-byte cap (all three in `download.luau`), and
Satset's token bucket (in its modes). NetRay's are off unless a schema declares them, so nothing is
lifted for it beyond a decode-work cap raised to the most its compiler takes, which one bench packet
needs. The checks behind those limits still run and are timed; only the refusals are gone. `Runtime`
and `Rivals` stop if any event fired goes unheard, the Studio tables report a tool's loss, and both
scripts print this line above their tables.

## Methodology
Each tool fires an event 1000 times a frame for 10 seconds. Each bench is a pool of payloads, fired in turn:
`Booleans` and `Entities` send the same payload every time, and `BooleansRandom` and `EntitiesRandom` send a thousand
different ones a frame, from a pool of 1001 so that no frame repeats the one before it. Roblox compresses a remote's buffers with zstd, so identical events compress to almost nothing
and their bandwidth measures the compressor; the random benches leave it nothing to find.

`Fire ms` is the CPU time a frame's thousand fires took on the client. Studio caps the framerate at 60, so a tool at
60 FPS is bounded by the cap, not by its own cost, and this column still tells such tools apart. Studio compiles
LocalScripts natively, which most clients do not, so every tool looks faster here than on a player's device.

`Bytes/event` is what an event cost on the wire after Roblox's compression: every byte the client sent from the first
fire until its backlog drained, less what it sends idle, over the events fired. `Drain` is how long that backlog took
after the last fire. This replaced a `Kbps` column that sampled `Stats.DataSendKbps` -- kilobytes a second, not
kilobits -- once a second and scaled it by 60 / FPS. That read low for every tool below 60 FPS, since what a slow tool
fired went out after its sample and after the run: on the M1, Packet's EntitiesRandom came to 486 bytes an event, less
than the 600 bytes of random data in it. Tables older than this change still carry the `Kbps` column, and it should be
read with that in mind: no tool encodes Entities in fewer bytes than another (see below).

BlinkBlox's inbound limits are raised in the definition file for this, since a live server's defaults refuse most of
what the benchmark sends -- that is what they are for.

Blink is the original project BlinkBlox forked from, at its last release. `--download` fetches its source
into `tools/upstream`, and its own compiler builds `definitions/Definition.upstream.blink`, the same events without the
inbound limits, which Blink does not have, and without `Tiny`.

## Without Studio

`luneblox run Runtime` in this directory times every tool above on LuneBlox, where Studio cannot: interpreted, as
most players' clients run code, and decoding on the server, which Studio does not time. It loads zap's and Blink's
generated modules, ByteNet, Packet, QuickNet, Warp and Satset from the same files Studio runs (after
`luneblox run build --download`), and NetRay's generated by its own compiler, with just enough of Roblox mocked
around them, and times a frame's thousand fires, the flush into packets, and the server decoding those packets and
calling its listener. `Bytes/event` is the encoder's output; `zstd` is that output compressed as Roblox would, at
zstd's default level, 3. Every level
from 1 to 9 gives the same and matches the Studio tables; Lune's own default, the highest, found three-byte repeats
Roblox does not and took BlinkBlox's index and length back from every random boolean array -- 125.81 bytes an event
where Studio measured 128.26. The tables measured before 2026-10-25 used it, so their `zstd` column for the
`Random` benches reads up to two bytes an event low for every tool that frames each event.

The runs below were made on 2026-09-29 on an Intel Core i7-13700K with 64 GB of memory, Windows 11, LuneBlox 0.10.9
(Luau 0.740), with this repository's compiler (0.42.0). Every run was the only one on the machine, pinned to one
performance core at high priority: the 13700K's efficiency cores run the same code several times slower, and runs
side by side on neighbouring cores moved an allocating decode by about 8%. Each figure is the median of three runs,
and each run's figure is itself a median or 99th percentile over 200 frames, in milliseconds per frame. `native` is
what a Roblox server runs; `interpreted` is what most clients run. Packet declares `--!native` nowhere, so both its
rows are interpreted. `Tiny` is BlinkBlox's alone.

Every row is timed in a process of its own (`Runtime` starts one for each bench, mode and tool), which holds 64 MB
from before the tool loads and runs a full garbage collection (`luau.collect()`, LuneBlox 0.10.9) before it measures.
In one process each tool inherited the heap and the allocator's state the tools before it left, and the first paid for
growing them: BlinkBlox, always first, decoded Booleans natively in 6.5 ms, and in 2.9 when it ran last, where QuickNet
took 3.6 in sixth place and 7.4 in first. The 64 MB stands for a game server's heap, next to which a tool's own
buffers are small: Luau's collector paces itself on the heap's size, and QuickNet keeps about 12 MB alive.

QuickNet and Warp keep their own limits in a game; here they are lifted as Packet's is. QuickNet's rate limit is set
to `math.huge` for every event, as QuickNet's own benchmark does, and Warp's server refuses a packet over 8000 bytes,
so `download.luau` raises that check to `math.huge`. Warp encodes nothing when an event is fired: it queues the value
and serialises the whole queue at its flush, which is why its fire column is near zero and its flush column is not.
It also sends each reliable packet as its XOR against the one before it, which is why its `zstd` column for the
repeated payloads is the lowest or tied here, where each frame is compressed on its own: two identical frames XOR to
zeros. In Studio it is the reverse (see Results below).

The tables measure QuickNet v0.3.5-beta and Warp 1.1.0-pre7. `download.luau` now fetches QuickNet v0.4.0-beta
(`edba9a2`) and Warp 1.1.0-pre8, and lifts QuickNet 0.4.0's new limits, a 50,000-byte packet and a hundred events in
one, as it lifts Packet's. One run of each pair on 2026-10-12, side by side on a 4-vCPU Linux container with
LuneBlox 0.10.17 and no core pinned, so a few percent is noise: QuickNet 0.4.0 fires Entities in 13.7 ms native and
31.1 interpreted, from 18.0 and 40.1, and decodes it in 28.2 and 51.4, from 32.1 and 61.0, with Booleans unchanged;
BlinkBlox fired the same Entities in 4.7 and decoded them in 12.9 there. Warp 1.1.0-pre8 times as pre7 did. It frames
unreliable packets as well now, each with a 2-byte header -- `SelfState` costs it 1,050 bytes a frame to 50 players,
from 950 -- and sends a whole packet once a second, so its `zstd` column on the repeated payloads rises with how many
frames a second it runs: Entities came to 0.07 bytes an event native and 0.20 interpreted, from 0.03.

Satset encodes each field through a function its schema holds, so it is slower to fire and decode everywhere, and
its flush scans the frame's batch a second time to merge runs: consecutive events of one id go under one 3-byte
header (5 past 255 events), with no index or length each. That is the one place it is smaller, by the byte of
index BlinkBlox writes before every event: 1.01 bytes a `Tiny` to 2.00. Compression keeps that byte on random
payloads: `BooleansRandom` cost Satset 127.02 bytes an event compressed to BlinkBlox's 128.01, and 127.15 to 128.26
in Studio (Results below). It batches unreliable events by default, one call for `UnreliableInput`
where BlinkBlox makes eight unless built with `BatchUnreliable`; an unreliable `FireAll` it copies to each player,
50 calls for `WorldState`. It has no Instance type and sits out `Instances`.

The mock players and Instances are userdata, as they are in a game. Before 0.40.0 they were tables, and native code
sends a function whose parameter is annotated `Player` or `Instance` back to the interpreter when a table arrives, so
some native figures in earlier tables were interpreted ones.

### NetRay

NetRay Compile v0.2.0 joined on 2026-11-23. It is an IDL compiler like BlinkBlox and zap, so the
comparison is the one this fork exists to publish. `--download` fetches its source, pinned at the
`v0.2.0` tag, and its own compiler builds `definitions/Definition.netray` and `Scenarios.netray` on
LuneBlox, as Blink's does; its CLI ships binaries for x86_64 alone, and none for the Apple silicon
this run was made on. Its generated Server and Client require a `Types` module beside them, so the
output directory is mounted as instances and the siblings resolve through `script.Parent`, as Rojo
builds it.

Its defaults are the inverse of every other rival's: validation off, and its per-event and
per-module limits off unless the schema declares them, so nothing is lifted to run it -- its own
`MaxDecodeWork` only has to cover what one bench packet decodes, 1000 events of 1000 elements, and
is raised to the most its compiler accepts because no honest client sends that. `option
DecodeStruct = Table` gives each struct payload one table argument, which is the shape every other
tool's mode presents; its `Instance` is a passthrough, a remote argument beside the buffer rather
than a reference inside one, and Roblox's own serialisation of it is not in the Bytes column.

Three runs of `Runtime` and `Rivals` on 2026-11-24, an Apple M1 MacBook Air with LuneBlox 0.11.4, no
core pinned, BlinkBlox 1.6.0 from this repository, each figure the median of the three and each run
alone in its own process, with the machine's ordinary background load (the quiet check in
`.lune/libs/runtime.luau` stayed silent). `NetRay `checked`` is the same events with
`Validate = Full`, receive budgets sized to fit, and `Compression: Repeat` on `Snapshot` -- the
configuration a live server wanting NetRay's safety features would run. `NetRay `fields`` is the
same with `Compression: Fields`, and `BatchUnreliable = false` rows are `Rivals -- --no-batch`: since
1.6.0 a client gathers a frame's unreliable events by default, so `UnreliableInput`'s eight fires
are one remote call, and that row is the same build with the gather turned off.

    instance list rests on -- and that check is what the fire pays for.
[^input]: The gather removed seven remote calls a frame; what the remaining fire does is write into the
    batch, count the packet's three limits and frame the entry, where NetRay's single write does not.

What the tables say:

- **BlinkBlox decodes a struct faster, by more than two and a half times on the thousand-event
  benches.** On `Entities` natively it decodes 1000 events in 3.8 ms where NetRay takes 10.0, and on
  `EntitiesRandom` 3.9 against 10.2. The gap is the read path: every guard BlinkBlox emits is
  written to a shape the native compiler keeps straight, while NetRay's decode returns an offset
  per field and re-checks the buffer bounds a field at a time; the two agree on what they refuse.
- **NetRay fires a struct as fast, and BlinkBlox's gather closes the call gap on inputs.** NetRay's
  `FireAll` writes straight into the outgoing arena; since 1.6.0 BlinkBlox splices the event's own
  write into its `FireAll` the same way, so on `Broadcast` its 100 structs cost 0.013 ms to fire to
  NetRay's 0.012 natively, and 0.026 against 0.029 interpreted -- the swap is gone. On `Tiny` --
  where the cost is framing, not data -- NetRay's 0.033 against BlinkBlox's 0.065: what is left of
  that gap is `Begin`, `Commit` and `Frame`, which measured cheaper as calls than written out.
  BlinkBlox's client write takes a lazy rollback, commits a run, and hands every fire to `Frame`
  before the packet is cut, and `Entities` interpreted stays NetRay's by the write's own shape,
  9.7 against 8.8.
- **The gather makes an input frame one call, as NetRay's is.** `UnreliableInput` fires eight
  events a frame: BlinkBlox's is one remote call, 40 bytes, 0.004 ms of fire, where the
  `BatchUnreliable = false` rows beside it are eight calls -- the shape every release before 1.6.0
  shipped. The decode is level, 0.001 against NetRay's 0.002. It is the client's fire that batched,
  not the server's send: a `Fire` to one player still goes at once (`SelfState`: 0.015 against
  NetRay's 0.016, 50 calls either way).
- **NetRay wins `Instances` -- on fire, decode and calls -- and BlinkBlox's bytes are the whole
  story there.** Its passthrough carries the part outside the buffer, so the 103 bytes a frame both
  report is BlinkBlox's entire encoding against NetRay's buffer plus an Instance Roblox serialises
  beside it, which this column does not count. Its fire is 0.004 ms to BlinkBlox's 0.027 natively
  because BlinkBlox's client writes the event through `Begin`/`Settle`, checks the packet's three
  limits and runs `Frame` -- a failed write must leave nothing behind, and that is what it costs.
  Interpreted, the decode is level, 0.019 apiece: a reference is an index into the packet's
  Instance list either way.
- **BlinkBlox writes fewer bytes wherever both send state.** `WorldState` costs it 12,900 bytes a
  frame to NetRay's 13,700 and `SelfState` 850 to 900: NetRay puts a `u16` index on every event
  where BlinkBlox frames a run of one index in three bytes, and its `u8`/`f32` struct is a byte
  longer. On `Broadcast` the two are a byte and a half an event apart, 85,150 to 85,000.
- **`Validate = Full` costs NetRay eight times its fire time, and buys nothing this harness can
  see.** A thousand booleans take 29.4 ms to fire natively rather than 3.5, a thousand entity
  structs 16.4 rather than 1.6, and the decode is the same: the checks are on the sending side,
  per element. Its receive budgets cost nothing measurable, as the `checked` rows beside the
  defaults show.
- **Its opt-in compression turns a broadcast into fifty sends.** `Compression: Repeat` keeps a
  baseline per recipient, so `FireAll` becomes a per-recipient `FireClient` per event: 150 calls a
  frame and 3.2 ms of fire to BlinkBlox's 0.013 and one call, and a frame's bytes rise to 95,000
  from 85,000 because the payloads differ index by index and the delta carries more than it saves.
  `Compression: Fields` -- a mask of the fields that moved -- finds nothing to mask in payloads that
  differ every frame, and costs more than `Repeat`'s scan where it is measured: 3.6 ms of fire and
  0.5 of flush against 3.2 and 0.43, with the same 95,000 bytes and 150 calls. Measured one at a
  time, validation alone added about half again to a `FireAll`'s fire time and nothing to its bytes
  or calls, and compression alone cost the rest: the `checked` row carries both. It is off by
  default, and this is why an entropy-coded delta is deferred here rather than assumed (`CLAUDE.md`,
  "Settled decisions").

### 1.4.0's run framing, every tool current -- 2026-11-14
Three full runs of `Runtime` and `Rivals`, each alone on one performance core, on the i7-13700K below
with LuneBlox 0.11.4 (Luau 0.740), BlinkBlox built from this checkout at 1.4.0. Tool versions: Blink
0.18.9, zap 0.6.29, ByteNet 0.4.3, Packet 1.7.0, QuickNet v0.4.0-beta (edba9a2), Warp 1.1.0-pre8 and
Satset 0.6.0. What changed in BlinkBlox since the tables above: four or more consecutive events of
one index in a batch travel under a shared 3-byte header -- 255, the index, the count less one --
with no index each, and 255 stops being an event index, so a channel numbers 0 to 254
(**Recompile both modules**; wire version 4).

The framing runs after each write returns -- the write itself is unchanged, three same-index entries
turn into a run when the fourth arrives, and every member after that moves its body one byte left
over the index it will not need -- so every send figure but the smallest moved under five percent:
a thousand one-byte events (`Tiny`) fire in 0.047 ms natively rather than 1.3.9's 0.028 and 0.256
interpreted rather than 0.126, still six times faster than the next tool. The decoder reads the
marker once and then that many events without an index each: every decode figure IMPROVED, by 0.5
to 5.3 percent. The bytes: 127.01 an event on the boolean benches (Satset's own run framing number,
tied), 601.01 on Entities (a byte under every other tool), and on `Instances` a frame's hundred
same-index events cost 103 bytes where every other tool pays 200 to 303.

## Results

The Studio run below was made on 2026-10-25 on an Apple M1 MacBook Air with BlinkBlox 1.3.1's
modules, three rounds of every tool on every bench, no core pinned, with nothing else running but the
desktop. Since 1.2.1 only the
server module asks to be compiled natively, so BlinkBlox's client is interpreted in Studio, as
Packet's is, while Blink's and zap's modules, QuickNet's functions (each marked `@native`) and the
busiest files of ByteNet, Warp and Satset are native: its `Fire ms` here is an interpreted figure
against native ones, and each fire table names how every tool's client is compiled. Interpreted
against interpreted, as most players' clients
run, `luneblox run Runtime` has it the fastest to fire both `Booleans` benches and tied with Blink on
both `Entities` ones (Warp aside, which encodes at its flush).
`Bytes/event` moves by about a byte an event from run to run, as BlinkBlox and QuickNet traded places
on `EntitiesRandom` between one run and the next, so each is the median of the three rounds, with the
lowest and highest round beside it: only a gap wider than that spread is a difference. A round can go
wrong outright -- one of BlinkBlox's `Entities` rounds read 0.00, its idle traffic overestimated --
and the median leaves it out. Satset's and Warp's `Entities` cost almost nothing because each sends
a reliable packet as its XOR against the last, and every frame of that bench is the same.

Warp's `Fire ms` is left out: its Fire only queues the value, and
it encodes the queue later in the frame on a signal of its own that the bench cannot time, so the
figure read 0.1 ms while its frame rate fell to 32. `luneblox run Runtime` times its fire and flush
together.
