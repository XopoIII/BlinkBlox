# Events
Events are BlinkBlox's version of Roblox's `ReliableEvent` and `UnreliableEvent`.<br/>
They are the main way to communicate between client and server.

## Usage in BlinkBlox

Events can be defined using the `event` keyword.
```blink copy
event MyEvent {
    From: Server,
    Type: Reliable,
    Call: SingleAsync,
    Data: f64
}
```

#### `From`
Determines the side from which the event is fired. <br/>
Currently BlinkBlox supports either `Server` or `Client`.

#### `Type`
Determines the type (reliability) of the event.
* `Reliable` - Events are guaranteed to arrive at their destination in the order they were sent in.
* `Unreliable` - Events are not guaranteed to arrive at their destination or to arrive in the order they were sent in. They also have a maximum size of roughly 1000 bytes, which BlinkBlox enforces at compile time and again on send -- see [`MaxUnreliableSize`](1-options#maxunreliablesize).
* `OrderedUnreliable` - As `Unreliable`, plus a two-byte sequence number: a packet that arrives *after* a newer one is discarded rather than delivered late. Delivery is still not guaranteed and packets can still be lost — what is guaranteed is that your listener never sees an older state after a newer one.

<Callout type="info">
    Use `OrderedUnreliable` for anything describing a **current** state — a position, an aim
    direction, a health value — where applying a stale packet makes the state visibly snap backwards.
    Plain `Unreliable` is right for independent one-off signals, where an older packet is still
    useful on its own.

    The sequence is tracked per event, and on the server per player in both directions: sixty clients
    each run their own counter, and the server counts what it sends to each of them separately, so a
    player left out of a `FireList` or `FireExcept` is never told that the next packet it does get is
    stale. It wraps at 65536: a packet counts as newer when it is less than half the counter's range
    ahead of the last one seen, so one from just before the wrap that arrives just after it is still
    recognised as old.
</Callout>

#### `Call`
Determines the listening API exposed on the receiving side.
* `SingleSync` - Events can only have one listener, but that listener cannot yield.
* `ManySync` - Events can have many listeners, but those listeners cannot yield.
* `SingleAsync` - Events can only have one listener, and that listener may yield.
* `ManyAsync` - Events can have many listeners, and those listeners may yield.
* `Polling` - Events are iterated through `Event.Iter()`.

#### `Poll`
Deprecated, and worth reading even if you have never typed it -- it may be in a schema you inherited.

`Poll: true` is the 0.x way of asking for polling. `Call` is still required beside it, and its value
is then **discarded**: an event declared `Call: SingleSync, Poll: true` compiles to `Polling`, not to
`SingleSync`. It went undocumented and unwarned for long enough that a schema using it had no way of
learning there was a current spelling.

It still works and now warns (`W3017`). Replace it with `Call: Polling` and delete the `Poll` line.

<Callout type="warning">
    A `Single` event keeps exactly one listener. Calling `.On()` a second time **replaces** the first
    and warns, rather than erroring -- but the displaced listener's disconnect function stops working
    at that moment, because it only detaches a listener that is still the current one.

    So two systems that each connect and later disconnect will leave a listener attached that neither
    believes it owns. If more than one place needs to hear an event, declare it `ManySync` or
    `ManyAsync`.
</Callout>

<Callout type="error">
    A `Sync` listener runs **on the decode thread**. Yielding in one therefore stops decoding the
    packet it arrived in, and the events behind it in that packet are lost -- see
    [`SyncValidation`](1-options#syncvalidation), which reports this but only once another packet
    turns up. Erroring in one is caught, but costs the rest of that packet just the same.

    Prefer `SingleAsync` or `ManyAsync` unless the per-event cost of a spawned thread genuinely
    matters to you.
</Callout>

#### `Rate`, `Burst`
Limits how often one player may send this event. Both fields are optional, and both are ignored on an
event the server sends -- only inbound traffic is limited.

`Rate` is the sustained number of events per second accepted from a single player. `Burst` is the
bucket capacity: how many may arrive at once before the rate applies. It defaults to `Rate` rounded
up, and may not be below 1: each event spends one whole token, so a smaller bucket would refuse every
event however long the client waited.

```blink copy
event Purchase {
    From: Client,
    Type: Reliable,
    Call: SingleAsync,
    Rate: 5,
    Burst: 10,
    Data: u16
}
```

Refused events are dropped before they reach your listener, and reported at most once per player per
event per second. To do something else about them -- log to your analytics, flag the account -- pass
a handler to `SetRateLimitHandler`. It is called on the same schedule as the warning, and `Refused`
is how many refusals that call stands for: the one that made it, and those counted since the last.
`Event` is `nil` when what was refused was whole packets over the
[inbound budget](1-options#inboundbytespersecond-inboundburst) rather than one event:

```lua copy
Net.SetRateLimitHandler(function(Player: Player, Event: string?, Refused: number)
    Analytics:Record(Player, Event, Refused)
end)
```

<Callout type="info">
    Nobody is kicked automatically. A false positive under server lag would eject a legitimate player,
    and whether that is the right response depends on the game -- so the decision is left to you.
</Callout>

The limit is checked after the event is deserialised and before it is dispatched. Payloads are
variable length, so an event cannot be skipped without reading it: the cursor would be left
mid-event and the rest of the packet would decode as garbage. What the limit saves is the listener
and the game logic behind it. Bounding the decoding itself is what
[`MaxEventsPerPacket`](1-options#maxpacketsize-maxeventsperpacket-maxinstancesperpacket) does.

A refused [function](6-functions.mdx) call is still answered -- with a failure, so the caller's
`Invoke` raises promptly rather than hanging.

See [`DefaultRate` and `RequireRates`](1-options#defaultrate-requirerates) for applying a limit
across a whole schema, and for making a missing one a compile error.

#### `Data`
Determines the data that is sent through the event, can be any [type](./4-types.mdx).<br/>
This field can be omitted if no data is required.

##### Type Packs
Multiple data values are supported through the usage of a type pack (commonly referred to as a tuple).
Type packs can be defined as a list of [types](./4-types.mdx) seperated by a comma within parenthesis.<br/>
For example, a type pack of different [number types](./4-types#numbers) can be written like so:
```blink  copy
event MyTypePackEvent {
    From: Server,
    Type: Reliable,
    Call: SingleAsync,
    Data: (u8, u16, u32)
}
```

Elements may be named. The name is what the parameter is called in the generated code, so a listener
reads `function(chefId, dish)` rather than `function(Value1, Value2)`:
```blink copy
event CookRequest {
    From: Client,
    Type: Reliable,
    Call: SingleAsync,
    Data: (chefId: f64, dish: string)
}
```

Naming is optional and may be partial: `(u8, named: string, u16)` is a valid pack, and the elements
left unnamed keep their positional `Value1`, `Value3`.

<Callout type="info">
    Naming an element changes the generated **signature** and nothing else. A type pack is serialised
    positionally, with no field tags, so a name costs nothing on the wire -- adding one to an existing
    pack does not change a single byte of what it sends, and the two sides stay compatible.
</Callout>

A name becomes a parameter of the generated `Fire` and `Invoke`, so it has to be usable as one: `end`,
`local` and anything that is not an identifier are refused at compile time, as are two elements
sharing a name, and the few names those functions already use themselves -- `Player`, `Buffer`,
`Instances`, `Load` and the like; the compiler says which. That is stricter than a
[struct](./4-types.mdx) field, which becomes a table key and may be any string. Inside the module the
elements travel under positional names, so a name can never collide with the serialisers' own.

## Usage in Luau

### Firing an Event
```lua filename="client.luau" copy
blink.MyEvent.Fire(5)
blink.MyTypePackEvent.Fire(2^8 - 1, 2^16 - 1, 2^32 - 1)
```
```lua filename="server.luau" copy
blink.MyEvent.Fire(Player, 5)
blink.MyEvent.FireAll(5)
blink.MyEvent.FireList({Player}, 5)
blink.MyEvent.FireExcept(Player, 5)
```

### Listening to an Event
```lua filename="client.luau" copy
blink.MyEvent.On(function(Value)
    -- ...
end)

blink.MyTypePackEvent.On(function(Foo, Bar, FooBar)
    -- ...
end)
```
```lua filename="server.luau" copy
blink.MyEvent.On(function(Player, Value)
    -- ...
end)

blink.MyTypePackEvent.On(function(Player, Foo, Bar, FooBar)
    -- ...
end)
```
```lua filename="disconnect.luau" copy
local Disconnect = blink.MyEvent.On(...)
Disconnect()
```

A reliable event that arrives while nothing is listening is queued, and the queue is handed to the
listener the moment one connects -- so a listener connected a frame late still sees what was sent
before it. The queue holds 256 events. On the server it is filled by clients, so once it is full
further events are dropped without a word: an event the game declares but never listens to cannot
be used to grow server memory or fill the output. On the client a full queue warns instead, because
there it usually means a listener somebody forgot.

### Packets that cannot be decoded
A packet that fails to decode -- truncated, carrying an index no event has, or failing a range --
is abandoned at the event that failed, since nothing after that point can be trusted. The server
says nothing about it by default, so that a client sending garbage every frame cannot flood the
output. To log it, flag the account or kick, install a handler:

```lua filename="server.luau" copy
blink.SetDecodeErrorHandler(function(Player: Player, Event: string?, Failure: string)
    Analytics:Record(Player, Event, Failure)
end)
```

`Event` is the event the packet claimed to carry, or `nil` if its index named no event at all. On the
client the handler takes `(Event, Failure)`, and without one the client warns, naming both.

On the server the handler is called at most once a second for each player, channel and event, like
the rate-limit handler: a client sending a bad packet every frame costs the game one call a second,
not one per packet. The server's own warnings about what a client sent -- a malformed packet, an
oversized one, too many instances, too many events -- keep the same schedule, per player.

An error thrown by a `Sync` listener is not a decode failure. It is raised as an error of its own,
the way an `Async` listener's is, and the rest of the packet is still delivered.

### Iterating an Event (Polling)
```lua filename="client.luau" copy
for Index, Value in MyEvent.Iter() do
    -- ...
end
for Index, Foo, Bar, FooBar in MyTypePackEvent.Iter() do
    -- ...
end
```
```lua filename="server.luau" copy
for Index, Player, Value in MyEvent.Iter() do
    -- ...
end
for Index, Player, Foo, Bar, FooBar in MyTypePackEvent.Iter() do
    -- ...
end
```

On the server a polled event's queue is filled by clients, so it stops taking rows at 256 for each
player the server can hold (`Players.MaxPlayers`). A game that iterates its polled events every frame
never comes near that; one that leaves an event unpolled no longer lets clients grow it without end.
