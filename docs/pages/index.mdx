# BlinkBlox

An IDL compiler written in Luau for ROBLOX buffer networking.

Describe your events and the shape of their data in a `.blink` schema; the compiler generates server,
client and shared Luau modules that pack them into buffers, validate what arrives, and batch what
leaves.

## This fork

A maintained fork of the project. Upstream stopped taking changes on this line of the compiler and
moved to a rewrite, leaving reported defects — including an unbounded parse of hostile client input —
closed as out of scope. This fork fixes them and continues from there:

- **Booleans and optional flags share a byte.** Eight of them cost one byte rather than eight; a
  struct with two booleans and two optionals, one absent, went from 5 bytes to 2.
- **Lengths are encoded relative to their minimum.** `u8[300..400]` spends one byte describing its
  length instead of two, and the same applies to bounded strings and buffers.
- **[`OrderedUnreliable`](language/5-events#type)** discards an unreliable packet that arrives after a
  newer one, so a position or aim direction never snaps backwards.
- **Rate limiting, per player and per event.** Declare `Rate` and `Burst` on an inbound event or
  function and the generated server spends tokens from a bucket before dispatching. Refused events
  are dropped and reported to a handler of your choosing rather than kicking anyone. Neither of the
  comparable compilers has this. See [`Rate`, `Burst`](language/5-events#rate-burst).
- **Unreliable events that cannot fit are refused at compile time.** Roblox drops an unreliable
  payload past ~900 bytes silently; the compiler measures every unreliable event, errors on the ones
  that can never fit, warns about the ones that might not, and names the field with no upper bound.
  A runtime check catches the rest and says which event lost the packet. See
  [`MaxUnreliableSize`](language/1-options#maxunreliablesize).
- **Inbound packets are bounded.** Packet size, decoded-event count and instance references are
  capped, an unrecognised event id stops the parse, and a truncated packet is contained instead of
  raising out of the remote handler. See [`MaxPacketSize`](language/1-options#maxpacketsize-maxeventsperpacket-maxinstancesperpacket).
- **A decoded length is checked before the read it authorises.** A length prefix is sized from the
  span of its declared range, so `string(0..64)` travels in a byte that holds 255 — the bound used to
  be checked only once the string existed, and an unbounded `buffer` was allocated at whatever size
  the packet asked for. Both are now checked first, and every variable-length read is additionally
  bounded by the bytes left in the packet.
- **A decode loop always has something to run out of.** The element count of an array or a map is
  read from the packet, so the work it buys has to stay proportional to what the packet paid. An
  element that reads bytes runs out of packet; one that takes a value from the instance table now
  runs out of instances, which `unknown` never checked. An element that does neither is refused at
  compile time -- `struct {}[]` turned two bytes into 65535 iterations. The count is also checked
  before `table.create` reserves the slots, so a `u8[]` claiming 65535 elements no longer buys the
  allocation on its way to failing.
- **A player who leaves mid-call no longer lingers** in the replication map, taking a buffer
  allocation and a remote call every Heartbeat for the rest of the server's life.
- **Instance classes containing a digit** — `Instance(Vector3Value)`, `Instance(Motor6D)` — parse.
- **Edit mode keeps the shape of the real API**, so Roblox stories no longer raise on stubs.
- **[`Predict`](language/1-options#predict)** delivers an event to local listeners without a remote,
  for tests and for stories.
- **Remote arguments are checked before they are trusted.** A client can call `FireServer` with
  anything; the generated handler establishes the argument types before reading them, stops decoding
  for a player who has left, and refuses a remote of the wrong class planted under the right name.
- **An answer reaches only the call it answers.** A call is known by its id and by its function, ids
  go round the whole u8 before one is reused, and each call's timer is cancelled once it is settled --
  so a late answer, an answer meant for another function, or an earlier call's timer cannot resume or
  fail a newer call. At most thirty-two calls wait at once.

## Performance

BlinkBlox aims to generate the most performant and bandwidth-efficient code for your specific experience.
Lower bandwidth usage translates directly into **lower ping\*** for players, and the generated
serialisers cost **less CPU** than a generalised networking library.

*\* Compared to standard ROBLOX networking. Not guaranteed in every case, but it should never make
ping worse.*

Benchmarks are available [here](https://github.com/XopoIII/BlinkBlox/blob/main/benchmark/Benchmarks.md).

## Security

Two things work against bad actors:

1. Data sent by clients is **validated** on the receiving side before it reaches game code, and the
   volume of that data is **bounded** before any of it is parsed.
2. Compression makes traffic **considerably harder to snoop on** than plain remotes.
