There are two benchmarks, and they answer different questions.

- **The runtime benchmark** times the generated code on
  [LuneBlox](https://github.com/XopoIII/LuneBlox) -- Lune on the Luau version Roblox runs, with
  Roblox's fast flags -- without Roblox. It is reproducible on any machine and
  separates the three things the code does: firing events, flushing them into a packet, and the
  server decoding that packet. It runs BlinkBlox, Blink, zap, ByteNet, Packet, QuickNet and Warp.
- **The Studio benchmark** puts the same tools and plain remotes inside Roblox Studio, and reports
  frame rate, the time the fires took, and bandwidth.

Blink is the original project BlinkBlox forked from, measured at its last release, 0.18.9, with the
same schema compiled by its own compiler.

## The generated code, on LuneBlox

Each frame fires 1000 events from the client, flushes them into one packet, and hands that packet
to the server. The times below are medians in milliseconds per frame, from 200 frames, and "bytes"
is the size of one event on the wire before Roblox compresses it. `Booleans` is `boolean[0..1000]`
holding 1000 values; `Entities` is 100 structs of six `u8` fields. The `Random` variants send a
thousand different payloads a frame instead of one payload a thousand times, and `Tiny` is a single
`u8`, where an event's cost is its framing rather than its data.

Three releases, each compiling the same schema, timed in one harness. Natively compiled, as a Roblox
server runs the module, fire / decode:

| Bench | 0.34.0 | 0.40.0 | 0.41.2 | Bytes |
|---|---|---|---|---|
| Booleans | 4.25 / 10.45 | **1.98** / 6.68 | 1.99 / **6.62** | 128 |
| Entities | 2.93 / 24.70 | 2.19 / **5.84** | **2.15** / 5.86 | 602 |
| BooleansRandom | 10.83 / 9.46 | 4.95 / 5.38 | **4.93** / **5.12** | 128 |
| EntitiesRandom | 2.95 / 26.17 | **2.47** / **8.03** | **2.47** / 8.06 | 602 |
| Tiny | 0.067 / 0.236 | 0.027 / **0.095** | **0.026** / 0.097 | 2 |

Interpreted, as most Roblox clients run it:

| Bench | 0.34.0 | 0.40.0 | 0.41.2 |
|---|---|---|---|
| Booleans | 37.28 / 42.40 | **17.11** / 20.56 | 17.12 / **19.89** |
| Entities | 13.31 / 33.46 | 12.94 / 16.25 | **12.77** / **16.19** |
| BooleansRandom | 37.12 / 42.09 | 18.11 / 19.01 | **17.99** / **18.86** |
| EntitiesRandom | 14.12 / 35.38 | 13.57 / **17.23** | **13.56** / 17.38 |
| Tiny | 0.166 / 0.381 | **0.125** / **0.242** | **0.125** / **0.242** |

The run was made on 2026-09-28 on an Intel Core i7-13700K with 64 GB of memory, Windows 11, on
LuneBlox 0.10.9. Each release compiled the schema to files first -- 0.40.0 and 0.41.2 with their
release executables, 0.34.0 from its source at the commit that released it -- and
`luneblox run Runtime -- --tools blink --sources <dir>` timed each in turn, five runs of each, one
at a time on one performance core, every figure the median of the five. An Entities event is a byte
shorter from 0.40.0 on: an array's length that needs two bytes of span is a varint, one byte under
128.

0.40.0 and 0.41.2 differ by no more than the runs do: on this schema their modules differ only by
four bound checks the newer one leaves out. What 0.40.0 changed against 0.34.0 is framing and
dispatch rather than the fields: one `pcall` a packet rather than one an event, none on a reliable
`Fire`, and a reader that keeps the packet in a local. That halves the boolean benches' fire and
decode, and takes Entities' decode from 24.7 ms to 5.8 natively. See the
[changelog](/BlinkBlox/changelog/).

Between single runs a decode figure moves by up to a sixth on this machine, so compare within a
column, or run both versions yourself, before reading a gap that small as a change. The flush, which
copies the batch into an exact-size buffer, took under 0.13 ms in every case. Entities' fire time
barely moves, natively or not, because there is nothing left to take out of it: each element is six
`buffer.writeu8` calls into a block allocated once for the whole array.

## Against other tools, on LuneBlox

The same harness runs every tool on the same payloads, from the same run and machine as above: three
full runs of `luneblox run Runtime`, each alone on one performance core, every figure the median of
the three. The versions were BlinkBlox 0.41.2, Blink 0.18.9, zap 0.6.29, ByteNet 0.4.3, Packet
1.7.0, QuickNet 0.3.5 and Warp 1.1.0-pre7.

"Send" is a frame's thousand fires and the flush that turns them into packets. Most tools encode as
they fire and flush in a fraction of a millisecond; Warp queues the values and encodes them all at its
flush, so only the two together compare. "Decode" is the server decoding those events and calling its
listener. Natively compiled is what a Roblox server runs; interpreted is what most players' clients
run. "Bytes" is one event as the encoder wrote it, before compression. Packet declares `--!native`
nowhere, so its native columns are interpreted too. The p99s and each column on its own are in
[`benchmark/Benchmarks.md`](https://github.com/XopoIII/BlinkBlox/blob/main/benchmark/Benchmarks.md).

Entities is where BlinkBlox's decode shows: a third of Blink's and zap's time natively, and under
half of every other tool's interpreted. Sending Entities costs BlinkBlox what it costs Blink, since
both write six `u8` fields into a block allocated once for the array.

Booleans is QuickNet's. Both pack a `boolean[]` eight to a byte, which makes the event an eighth of
what Blink, zap, ByteNet and Packet send, and QuickNet decodes the array in less time than
BlinkBlox: 4.13 ms against 6.53 natively, 14.86 against 18.09 interpreted. BlinkBlox checks what it
reads before a listener sees it -- the length against its bounds, before it allocates -- and runs the
listener in a `pcall`. Sending, the two are within a few percent of each other.
With a different array in every event the natively compiled decodes are level too, 4.06 against 4.30.

Warp encodes at the flush, and its send is two to nine times BlinkBlox's natively, two to five and a
half interpreted. ByteNet and Packet spend a byte on each boolean, and are the slowest to
decode everywhere.

## Sending to a crowd, unreliable events and Instances

The benchmark above sends in one direction, a thousand reliable events a frame from a client. A game
also has the server sending to a crowd, small unreliable events every frame, and events carrying
Instances. `luneblox run Rivals` runs those on every tool, on the same machine as the tables above;
each figure is the median of five runs, in milliseconds a frame, natively compiled, send (fire and
flush) then decode, with the remote calls a frame summed over every player reached.

| Scenario | BlinkBlox | Blink | zap | ByteNet | Packet | QuickNet | Warp |
|---|---|---|---|---|---|---|---|
| **Broadcast**: 100 structs a frame to 50 players, `FireAll` | **0.020**, **0.016**, **1 call** | 0.955, 0.027, 50 calls | 1.010, 0.026, 50 calls | 0.049, 0.108, **1 call** | 0.089, 0.185, **1 call** | 0.334, 0.040, 50 calls | 2.569, 0.125, 50 calls |
| **UnreliableInput**: 8 small inputs a frame, client to server | **0.002**, 0.004, 8 calls | **0.002**, 0.003, 8 calls | 0.003, **0.002**, 8 calls | 0.003, 0.008, **1 call** | no unreliable channel | **0.002**, 0.003, **1 call** | 0.004, 0.008, **1 call** |
| ... with `BatchUnreliable` | **0.002**, **0.002**, **1 call** | | | | | | |
| **Instances**: 100 events a frame carrying a part | **0.005**, 0.021 | **0.005**, 0.013 | 0.006, **0.009** | 0.031, 0.091 | 0.039, 0.124 | 0.014, 0.027 | 0.031, 0.089 |
| **WorldState**: 16 units a frame to 50 players, unreliable | **0.002**, **0.001**, **1 call** | **0.002**, 0.004, **1 call** | 0.003, 0.004, **1 call** | 0.008, 0.009, **1 call** | no unreliable channel | 0.014, 0.003, 50 calls | 0.204, 0.006, 50 calls |
| **SelfState**: each of 50 players their own unit, unreliable | **0.012**, **0.001** | 0.013, **0.001** | 0.016, **0.001** | 0.033, 0.002 | no unreliable channel | 0.025, **0.001** | 0.047, 0.002 |

A reliable `FireAll` in BlinkBlox is written once into a broadcast batch and sent in one
`FireAllClients`; Blink and zap copy it into every player's batch and send each one, and QuickNet
and Warp batch a frame per player too, so a send to 50 players is 50 remote calls. ByteNet and
Packet share a buffer as BlinkBlox does, and BlinkBlox decodes its packet in a seventh of ByteNet's
time and under a tenth of Packet's. `BatchUnreliable` gathers a client's inputs into one remote call, as
ByteNet, QuickNet and Warp do. On Instances BlinkBlox spends more than Blink and zap on the server,
for the checks it makes before a listener sees one: the class of each Instance, and a `pcall` around
the listener. Every scenario interpreted, and each column on its own, is in
[`benchmark/Benchmarks.md`](https://github.com/XopoIII/BlinkBlox/blob/main/benchmark/Benchmarks.md).

### A schema with many events

`luneblox run Scenarios -- ManyEvents` sends 100 reliable events a frame spread over 128 declarations, the
shape of a game with many remotes rather than one hot one, and times the client decoding them. The
event an index names used to be found by comparing it with every declaration before it; it is now
found by halving the range, down to runs of eight. Measured when that changed, on 2026-09-28 on an
Apple M1 with Lune 0.10.5, interpreted, as most clients run it -- medians of three runs taken
alternately, both versions' modules loaded from files:

| Scenario | 0.40.0 | 0.41.0 |
|---|---|---|
| **ManyEvents**: 100 events over 128 declarations, decode | 0.086 ms | **0.053 ms** |
| **Broadcast**, same schema: every event is the first declaration | **0.090 ms** | 0.093 ms |

The first declaration of a large channel pays for it: it was one comparison away and is now a few.
A channel of up to eight declarations, which covers every other benchmark here, compiles exactly as it
did.

These figures have no native row because they were taken on Lune 0.10.5, which could not give one:
its Luau 0.709 leaves a whole module interpreted once any function in it is too large to compile, and a
module's top-level function grows with every declaration, so the server module stopped compiling
natively at about 70 events and the client's at about 85. Current Luau leaves only that top-level
function interpreted, which runs once when the module is required. On LuneBlox, which runs it, the 128
declarations compile: on the i7 above, 0.024 ms to fire and 0.013 ms to decode natively, against
0.034 and 0.025 interpreted (medians of five runs). Roblox runs current Luau, so a game's large
module is native where it matters.

Streams have no counterpart in the other tools. `luneblox run Scenarios` times them for BlinkBlox: a
stream of 16 units to 50 players takes one `FireAllClients` a frame and 0.006 ms to flush natively,
and a stream held per player 0.036 ms for all fifty (0.013 and 0.080 interpreted).

## The cost of a remote call, in Studio

Measured in Studio on the Apple M1: a client firing a 40-byte buffer 240 times a second, or a
160-byte one 60 times a second -- the same 9 600 bytes a second -- read from
`Stats.DataSendKbps`, the median over eight seconds.

| Remote | 240 calls of 40 bytes | 60 calls of 160 bytes |
|---|---|---|
| `UnreliableRemoteEvent` | 13.2 KB/s | **11.2 KB/s** |
| `RemoteEvent` | 13.0 KB/s | **10.9 KB/s** |

That is about 11 bytes a call beside the payload, which is why a client sends at most
[`ClientFlushRate`](/BlinkBlox/language/options/#clientflushrate) times a second, 60 by default. The
same session sent 60 to 480 calls a second on each remote for five seconds: every call arrived, no
warning was printed and the ping did not move, so Roblox enforces no rate of its own to stay under.

## Against other tools, in Studio

Each tool fires 1000 events a frame for ten seconds, and every tool received everything it sent. The
numbers below are medians. The percentiles, and the harness itself, are in
[`benchmark/Benchmarks.md`](https://github.com/XopoIII/BlinkBlox/blob/main/benchmark/Benchmarks.md).

The run was made on 2026-09-28 on an Intel Core i7-13700K with 64 GB of memory, in Roblox Studio,
with nothing else open. The versions were BlinkBlox 0.41.2, Blink 0.18.9, zap 0.6.29, ByteNet
0.4.3, Packet 1.7.0, QuickNet 0.3.5 and Warp 1.1.0-pre7.

"Fire ms" is the CPU time a frame's thousand fires took on the client. It is the column to read when
two tools are both at Studio's 60 FPS cap. Warp only queues a value when it is fired and encodes the
queue later in the frame, so its fire time is near zero and its cost shows in the frame rate
instead. "Bytes" is what one event cost on the wire after Roblox compressed it: every byte the
client sent from the first fire until its backlog drained, less what it sends idle, over the events
fired.

The payload is an array of 1000 `true` values: `boolean[0..1000]`.

|---|---|---|---|
| Roblox remotes | 15 | 26.00 | 7101 |
| **BlinkBlox** | **60** | 1.92 | **0.04** |
| Blink | **60** | 4.52 | 0.13 |
| zap | **60** | 12.15 | 0.13 |
| ByteNet | 30 | 17.45 | 0.13 |
| Packet | 35 | 27.31 | 0.13 |
| QuickNet | **60** | 1.89 | **0.04** |
| Warp | **60** | **0.10** | 0.15 |

The same array a thousand times compresses to almost nothing for every tool. BlinkBlox's and
QuickNet's are smaller still because both pack a
[`boolean[]`](/BlinkBlox/language/types/#arrays-of-booleans) eight elements to a byte before the
compressor sees it. The others spend a whole byte on each boolean.

rate cannot tell them apart, and on the Entities benches QuickNet ran at 1.3 times Blink's.

## Reading the numbers

<Aside type="caution" title="60 FPS is Studio's cap">
Studio does not render faster than 60 frames a second. A tool at 60 FPS is limited by the cap, not by
its own cost, so on the boolean benches the frame rate shows only that BlinkBlox kept up. The fire
time is not capped, and it shows by how much.
</Aside>

<Aside type="caution" title="Bytes are counted after compression">
Roblox compresses a remote's buffers with zstd before they go out, and the Bytes column is what is
left. When every event in a packet is the same, the packet compresses to almost nothing, and the
number measures the compressor rather than the encoding. The `Random` benches leave it less to
find. Earlier runs reported a Kbps column instead, sampled once a second and scaled by 60 / FPS.
That read low for every tool below 60 FPS, because what a slow tool fired went out after its sample:
Packet's EntitiesRandom came to 486 bytes an event, less than the 600 bytes of random data in it.
</Aside>

- **Studio runs LocalScripts natively compiled, and most clients do not.** Studio compiles the
  client's code to native instructions, but Roblox's documentation describes native code generation
  as a server feature. So every tool looks faster in Studio than on a player's device. The Lune
  benchmark reports both.
- **The inbound limits are raised for the run.**
  [`benchmark/definitions/Definition.blink`](https://github.com/XopoIII/BlinkBlox/blob/main/benchmark/definitions/Definition.blink)
  sets the following options far above their defaults:
  - [`MaxPacketSize`](/BlinkBlox/language/options/#maxpacketsize-maxeventsperpacket-maxinstancesperpacket)
    and `MaxEventsPerPacket`;
  - `InboundBytesPerSecond` and `InboundBurst`.

  A thousand events a frame is a flood, and with the defaults a live server refuses most of it.
  Refusing it is the purpose of those limits. The checks still run, so their cost is included in the
  numbers above. See [Securing the server](/BlinkBlox/guides/securing-the-server/).
- **Packet's inbound limit is raised the same way.** Packet's server drops whatever a player sends
  past 8000 bytes a heartbeat, and it has no option to change that, so the harness patches the
  constant in the downloaded copy
  ([`benchmark/download.luau`](https://github.com/XopoIII/BlinkBlox/blob/main/benchmark/download.luau)).
  Left alone, Packet would lose nearly every event and the tables would have nothing to show for it.
  Packet has no packed boolean array, so its `Booleans` payload is an array of `Boolean8`, a byte per
  value, as ByteNet's is.
- **QuickNet's and Warp's limits are lifted too.** QuickNet allows each event 60 fires a second by
  default; the harness sets `SetRateLimit(math.huge)` on every event, as QuickNet's own benchmark does.
  Warp's server refuses a packet over 8000 bytes, and `download.luau` raises that check to
  `math.huge` as it does Packet's. Neither is on Wally at the version compared, so both are fetched
  from their GitHub source: QuickNet at commit `f7cfdf5` (0.3.5), Warp at its `1.1.0-pre7` tag.
- **Warp sends each reliable packet as its XOR against the last.** Two identical frames XOR to
  zeros, which zstd removes, so on the repeated payloads Warp's compressed bytes are the lowest of
  any tool. The `Random` benches draw from 1001 payloads, one more than a frame fires, so that no
  frame repeats the one before it and Warp's compression has as little to find as everyone else's.
- **The events go from client to server.** That direction is the one BlinkBlox validates.
  Every event is checked before a listener sees it.
- **Bandwidth depends on your schema.** These two payloads are simple. Where a schema has bounded
  lengths, optionals or booleans spread across structs, the savings come from the techniques in
  [Bandwidth and sizes](/BlinkBlox/guides/bandwidth/).
- **A different machine gives different numbers.** The ratios between the tools are the useful part.

## Running them yourself

The harness lives in [`benchmark/`](https://github.com/XopoIII/BlinkBlox/tree/main/benchmark) and
runs on Windows, macOS and Linux, on [LuneBlox](https://github.com/XopoIII/LuneBlox): `rokit install`
in the repository installs the version it pins. Run on anything else, each benchmark says so before
and after its figures, and names the runtime in its header, because the figures would not be
comparable. The same schema's modules, timed on Lune 0.10.5 and on LuneBlox, each figure the median
of three runs. On the Intel Core i7-13700K above, with LuneBlox 0.10.9:

| | Lune 0.10.5 | LuneBlox, Roblox's flags | LuneBlox, Luau's defaults |
|---|---|---|---|
| Luau | 0.709 | 0.740 | 0.740 |
| Entities, interpreted: fire / decode (ms) | 15.08 / 23.34 | 13.13 / 17.35 | 13.11 / 17.69 |
| Entities, native: fire / decode (ms) | 1.58 / 5.67 | 2.17 / 6.07 | 1.33 / 5.42 |
| 128 declarations, native: fire / decode (ms) | 0.024 / 0.011 | 0.024 / 0.013 | 0.024 / 0.013 |

On an Apple M1, with LuneBlox 0.10.6:

| | Lune 0.10.5 | LuneBlox, Roblox's flags | LuneBlox, Luau's defaults |
|---|---|---|---|
| Luau | 0.709 | 0.740 | 0.740 |
| Entities, interpreted: fire / decode (ms) | 33.47 / 48.53 | 15.38 / 20.70 | 15.44 / 20.82 |
| Entities, native: fire / decode (ms) | 3.23 / 10.91 | 3.92 / 10.83 | 2.57 / 9.07 |
| 128 declarations, native: fire / decode (ms) | 0.078 / 0.053 | 0.043 / 0.022 | 0.046 / 0.024 |

Interpreted code, which most players' clients run, is faster on LuneBlox on both machines, and by
how much depends on the machine: under half the time on the M1, where Lune's size profile built Luau
at `-Os` and LuneBlox builds it at `-O3`, and a seventh to a quarter less on the i7. Native code on
the thousand-event benches is slower with Roblox's flags than with Luau's defaults on both: Roblox
sets `DebugCodegenOptSize`, which skips a native optimisation, and the middle column is what a Roblox
server gets. `LUNE_ROBLOX_FFLAGS=0` gives the last column. On the i7 the 128 declarations ran
natively even on Lune 0.10.5 -- 0.024 / 0.011 against 0.038 / 0.025 interpreted -- where on the M1
that module stayed interpreted.

A processor with performance and efficiency cores, as the i7-13700K has, runs the same code several
times slower on the latter. The figures here were taken with each run pinned to one performance core
at high priority, one at a time; on Windows,
`start "" /b /wait /high /affinity 4 luneblox.exe run Runtime` pins a run to the second logical
processor.

- `luneblox run Runtime` times the generated code. `luneblox run Runtime -- Entities` runs only the benches
  whose name contains `Entities`, `luneblox run Runtime -- --frames 50` makes the run shorter, and
  `luneblox run Runtime -- --tools blink,zap` runs only the tools listed. The harness knows BlinkBlox as
  `blink` and Blink as `upstream`; the others by their lower-case names.
  `luneblox run Runtime -- --tools blink --sources <dir>` times the `Server.luau` and `Client.luau` in a
  directory instead of generating them, for comparing releases: compile the schema with
  `option ManualReplication = true` for it.
- `luneblox run Scenarios` and `luneblox run Rivals` time a server sending to a crowd, unreliable events,
  streams and Instances: BlinkBlox alone, and every tool. `--batch` builds BlinkBlox with
  `BatchUnreliable`; `Rivals` takes `--tools` as `Runtime` does.
- `luneblox run Performance` times the compiler itself: lexing, parsing and generating the test schema.
- `luneblox run build --download --run` fetches zap, BlinkBlox, ByteNet and Packet for the machine it
  runs on, QuickNet and Warp from their GitHub source, and the source of Blink, the original project, builds the Studio place, runs it with `run-in-roblox`, and
  writes `Benchmarks.md`. Press F5 when Studio's Output asks. Without `--download` it reuses the tools it has; without `--run` it
  only builds the place. `--local` compiles the schema with the checkout's own compiler rather than
  the latest release, which is how the numbers above were taken.
- `luneblox run Probe` measures how large an unreliable payload Roblox delivers, in both directions. It
  is what [`MaxUnreliableSize`](/BlinkBlox/language/options/#maxunreliablesize) was set from.
